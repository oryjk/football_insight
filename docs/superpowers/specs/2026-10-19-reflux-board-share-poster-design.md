# 回流看板分享图设计

日期：2026-10-19
状态：待实现（设计由 Claude 与产品负责人讨论后撰写）
前置：`2026-10-19-share-source-attribution-design.md`（分享来源参数，先做或同时做）

## 背景与目的

产品负责人在抖音发布的回流看板截图是迄今播放量最高的内容（约 1–2 万，其余几十），
说明「哪些座位回流了」是这个产品最有传播力的素材。球迷也会在群里互相转告「有票了」。

目前用户想分享，只能手动截屏：截图不规整、没有品牌、没有二维码，别人看到后无法一步进入。
本功能让用户在回流看板上一键生成规整的分享图，带小程序码，
**把每次转发变成一个可度量的拉新入口**。

## 目标

1. 在回流看板（历史复盘、当前比赛）生成一张分享图，可保存到相册、可发给朋友/群。
2. 图中带小程序码，扫码进入回流看板，来源为 `src=share&cid=ticket_poster`。
3. 分享图**不泄露付费价值**（见下方「内容边界」）。

## 非目标

- 不做图片的服务端渲染，沿用小程序 canvas（话题详情、赛季海报已有同类实现）。
- 不做实时推送、群提醒、订阅消息。
- 不做付费门槛：生成分享图免费，否则分享会减少。
- 不做其他球队的专属样式；球队切换（成都蓉城 / 云南玉昆）时以页面当前展示的比赛为准。
- 不使用俱乐部队徽或官方商标。球队名使用文字，沿用页面现有的展示方式。
- 不展示任何博彩赔率。

## 反目标

- 分享图让非会员无需付费就获得「实时、座位级」的回流信息，削弱付费价值。
- 把用户的账号信息（昵称、手机号、会员等级、用户 ID）画到图上。
- 生成失败时页面无反馈，或把按钮卡在加载状态。
- 数据过期的图被当成实时信息传播而没有任何时间提示。

## 内容边界（重要）

付费价值是「更早看到回流」。分享图是传播内容，必须按下面划线：

**图上只能出现用户当前页面已经能看到的数据**，不为生成图额外请求更高权限的数据。
在此基础上：

### 历史复盘图（比赛已结束，价值在于复盘）

可以包含：

- 对阵双方、比赛日期；
- 开售 10 分钟之后的回流合计次数（沿用页面现有统计口径，见 `AGENTS.md`「统计口径」）；
- 回流最集中的时间段、区域或价位（至多前三项）；
- 统计口径一句话说明；
- 生成时间。

比赛结束后的信息没有抢票价值，可以相对丰富。

### 当前比赛图（实时，价值在于时间差）

只展示**场次级汇总**，不展示座位级细节：

- 对阵双方、比赛日期、开售状态；
- 页面已展示的回流次数汇总（若该用户当前档位下看不到则不显示该项）；
- **数据截至的具体时间**（精确到秒），图上同时注明「实时库存变化很快，请以小程序为准」；
- **不包含**具体看台、区块、座位、价位明细。

理由：座位级明细是会员的核心价值，也是机器人最需要的信息；场次级汇总足以做内容传播，
并能把对方引到小程序看细节。

> 此边界是设计默认值。如果产品负责人后续希望放宽（例如允许展示区域级信息），
> 作为单独决定处理，实现方不要自行放宽。

## 方案

### 1. 入口

在回流看板页面（`pages/ticket-watch/index.vue`）加「生成分享图」按钮：

- 历史复盘页签：当前所选比赛有数据时显示；
- 当前比赛页签：存在当前比赛且有可展示数据时显示。

按钮放在不会挤压付费墙区域、不改变现有布局节奏的位置，具体由实现方参考页面决定。
审核状态（`systemConfigUnderReview`）下的行为沿用页面现有处理，不要因本功能绕过。

### 2. 画图

- 复用 `src/utils/canvasPoster.ts` 的 `traceRoundRect`、`flushCanvas`、`exportCanvasToTempFile`。
- 参考 `pages/topic-detail/useTopicShareCard.ts` 的串行绘制和版本失效模式（防止快速切换比赛时
  导出旧图）。
- 赛季海报页的「保存到相册并处理授权被拒」逻辑（`pages/season-recap/poster.ts` 的
  `saveRecapPoster`）目前在页面目录内。页面之间不能互相 import，
  **把它抽到 `src/utils`**（例如并入 `canvasPoster.ts`），赛季海报改为引用，
  保证赛季海报的行为和已有测试不变。
- 画布尺寸 750 × 1080 左右，具体由实现方定。配色沿用海报风格的固定色板
  （图片导出不受主题影响，赛季海报同款做法），主角是回流次数。
- 文本换行、截断使用已有的不拆分 Unicode 的工具思路（`wrapShareCardText`），长队名不溢出。

### 3. 小程序码

需要一个后端接口返回小程序码。现有 `season_recap/adapters/wechat_code.rs` 只服务赛季海报，
场景值写死。新增一个很小的接口，**不要改动赛季海报的行为**：

- `POST /api/v1/share-codes/ticket-watch`，需要登录（与赛季海报码一致）。
- 固定参数：`scene = "s=share&c=ticket_poster"`，`page = "pages/ticket-watch/index"`，
  `check_path = false`，`env_version = "release"`，宽度 280。
- 场景值固定、不含任何用户信息或比赛 ID，因此可以服务端缓存（24 小时，失败短缓存 30 秒，
  与现有实现一致）。
- 复用已有的 `stable_token` 取 token 方式，不强制刷新 token，避免影响其他使用方。
- 遵循项目分层（`domain` / `ports` / `application` / `adapters`），在 `bootstrap.rs` 装配。
  可以新建模块 `share_code`，也可以把现有二维码适配器抽出共用，由实现方决定，
  但改动不能影响赛季海报的测试。
- 小程序正式版先发布，再推广分享图：`check_path=false` 只解决生成阶段，
  不解决旧版本扫码后页面缺失。这一点已在赛季海报中处理过，沿用同样的发布顺序。

### 4. 落地行为

扫码进入 `pages/ticket-watch/index` 的普通默认视图，不做按比赛跳转。
海报上的二维码旁文案写「扫码看实时回流」。来源由 `App.vue` 现有逻辑捕获，无需改动。

### 5. 分享方式

生成后展示图片预览，提供「保存到相册」。用户也可以通过预览长按发送给朋友。
首版不额外做「直接发给微信好友」按钮，普通页面分享按钮（带 `ticket_current` /
`ticket_history` 来源）保持不变。

### 6. 失败与边界

- 小程序码获取失败：仍可生成不含二维码的图，并给出提示「二维码暂时获取失败」；
  或阻止生成并提示重试。**由实现方选一种并写进验证报告**；无论哪种，用户都必须得到明确反馈。
- 比赛数据为空：不显示入口。
- 数据加载中点击：按钮禁用，不重复生成。
- 切换比赛或页签时旧的生成任务作废，不得保存/展示旧图。
- 保存相册被拒：沿用赛季海报的授权引导。

## 度量

不新增表。扫码带来的注册在 `f_i_user_acquisitions` 中为 `src='share'`、
`cid='ticket_poster'`，与普通页面转发（`ticket_current`、`ticket_history`）可以分开比较。

可选：若现有用户行为上报（`reportPageActivity` 等）能在不改后端的前提下记录
「生成分享图」次数，则加上，用于计算「生成 → 扫码注册」的转化。不能就不加，不要为此改后端。

## 验收标准

1. 历史复盘图与当前比赛图都能生成、预览、保存。
2. **内容边界**：当前比赛图中不出现看台、区块、座位、价位明细；
   用单元测试覆盖「由页面数据构造画图内容」的纯函数，断言当前比赛图的内容集合不含这些字段。
3. 图上无昵称、手机号、用户 ID、会员等级。
4. 当前比赛图带精确到秒的数据截止时间和过期提示。
5. 二维码扫码后进入回流看板，新用户来源为 `src=share`、`cid=ticket_poster`。
6. 快速切换比赛或页签后点击生成，导出的图与当前所选比赛一致。
7. 抽出的相册保存逻辑不改变赛季海报的行为，其已有测试仍通过。
8. 后端：新接口有测试（请求体字段、未配置凭据时的失败、缓存行为），赛季海报测试不受影响。
9. 通过：后端 `cargo test`；小程序 `bun run type-check`、`bun test`、
   `bun run check:boundaries`、`bun run verify:mp-components`。
10. 真机验证（微信开发者工具不够）：canvas 导出、保存相册、扫码，并确认小程序码
    在正式版可识别。

## 交给实现方决定

- 按钮位置与图的视觉。
- 后端模块形态（新建或抽取共用）。
- 二维码获取失败时的降级方式（见上）。
- 画图所用的具体字段映射（以页面已有数据为准，不新增后端接口）。

## 提示

- 本地后端连接的是生产 `football_data`，测试不要用真实用户数据写入。
- 迁移无需，本功能不新增表。上线需要部署后端并发布小程序，部署后端后小程序才能获取码。
- 部署顺序：先部署后端，再发布小程序，最后才在抖音等渠道推广。
- 小程序版本号由发版脚本分配，不要手改。
