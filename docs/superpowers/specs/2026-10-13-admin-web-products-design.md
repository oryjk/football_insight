# Football Insight Web 管理后台与商品管理设计

状态：2026-10-13 本地实现与验证完成，生产未发布。用户已授权新建纯前端后台及补齐现有 Rust 后端接口。

## 目标与范围

在当前 monorepo 新增独立纯前端项目 `football_insight_admin_web`，使用与
`/home/betalpha/projects/betalpha-admin/admin-frontend` 相同的技术栈和技术规范。
后台供管理员维护目前手工写入数据库的会员商品及微信道具映射，首个左侧菜单为「商品管理」。
首版完成管理员登录和商品增删查改、启停、查询，不增加其他业务菜单。

新项目不包含服务端、数据库连接或微信密钥。真实落库需要在现有 Rust 后端新增
Admin API；用户已确认允许扩展现有后端完成真实 CRUD。

## 现状与约束

- 后端已有 `/api/v1/admin/auth/login`、`me`、`logout` 和独立 Admin JWT 会话；
  复用现有管理员账户，不使用小程序用户登录。
- 微信道具来源为 `f_i_virtual_payment_products`，下单实时读取。
  主键 `product_key` 为业务规格加实付金额，例如 `membership:V6@3900`。
- 表已有名称、微信道具 ID、金额（分）、启用状态、备注、允许购买账号 UUID 数组及时间戳。
  实施期间工作区新增会员有效期字段 `membership_duration_months`，接入管理表单，默认 12 月，
  范围为 1–1200 整数月；有效期随订单快照保留，管理接口变更不会修改历史订单。
- 支持 V6–V9 普通会员及限定账号的 V3 测试商品；V3 的允许购买账号不能为空。
  同一等级可能有多个实付金额映射，用于会员升级补差价。
- 公开会员展示和标价来自 `f_i_system_configs.membership_product`，不能把微信道具金额
  误认为修改公开会员标价的入口。首版管理微信道具记录，表单明确标注「道具金额」，
  提示金额须与微信已发布道具和业务实付金额一致，不自动改等级权益或公开标价。
- 用户描述现有两条商品；页面以 API 实时返回为准，不在前端写死或初始化这些记录。
- 当前工作区包含未提交的支付改动；实现须保留，并兼容新增的账号限制字段。
- 本地联调后端可能连生产数据库；验证写操作使用隔离测试数据库。

## 方案选择

推荐独立 Web 前端复用现有 Admin 身份系统，并为现有商品表新增真实 CRUD API。
这能满足用户从页面维护商品的完整目标，业务仍归属当前 Rust 后端。

仅实现前端并预留 API 能完成界面，但无法维护真实数据；只在用户明确选择该范围时采用，
接口缺失必须显示清楚，不能以本地存储或模拟数据冒充保存成功。

把功能并入 H5 或参考中台与新增独立项目的要求不一致，不采用。

## 技术与目录

React 19、Vite、TypeScript、Bun、Tailwind v4、shadcn/ui（new-york、neutral）和 lucide 图标。
只引入首版所需依赖，不复制参考后台的其他业务模块。

```text
football_insight_admin_web/
  src/App.tsx
  src/api.ts
  src/apiClient.ts
  src/authSession.ts
  src/theme.ts
  src/layout/
  src/components/ui/
  src/features/products/
  src/styles.css
  src/styles/{tokens,foundation,login,shell,workspace,products,responsive}.css
  README.md
  AGENTS.md
```

API 请求与错误处理、会话存储、商品表单校验与请求转换分别独立。React 组件使用 PascalCase
`.tsx`，与组件配套的纯逻辑文件使用 camelCase `*Model.ts`，文件基名不得仅大小写不同。
开发与构建统一使用 Bun，构建包含 TypeScript 检查。
Vite 代理 `/api` 到可配置的本地后端；生产使用同源 API，静态构建路径可配置。

## 界面与交互

沿用参考后台的深蓝黑默认主题、青绿强调色、可切换浅色主题；主题偏好使用本项目独立
存储键，并在渲染前应用。所有颜色、字号、间距和圆角引用 Token。
页面使用语义类名，Tailwind 仅用于基础 UI 组件；通用控件复用 shadcn，不重复手写。

桌面端固定左侧侧栏，首个且当前唯一业务菜单「商品管理」；顶栏显示页面标题、管理员身份、
主题切换及退出；业务筛选、操作和表格集中在主内容容器。窄屏侧栏使用抽屉，表格允许横向滚动。

商品页提供关键词、会员等级、启用状态筛选及分页，展示名称、等级、道具 ID、金额、有效期、
启用状态、购买范围、更新时间及行操作。提供刷新、新建、查看、编辑、启停和删除。
金额前端显示为元，传输和存储使用整数分，避免浮点误差。

新建/编辑表单包含名称、会员等级、道具 ID、道具金额、会员有效期（月）、启用状态、允许购买账号 UUID 和备注。
新建默认停用。业务键由等级和金额生成，不要求管理员手写；编辑等级或金额时，
后端在事务内同步更新业务键并检查冲突，前端使用响应中的新键，不能覆盖另一条映射。
表单明确提示这种修改会影响新购买需要匹配的规格。
V3 必须填写允许购买账号，其他会员空数组表示公开商品。

危险操作显示商品名称和影响，删除需明确确认。提交期间防重复；失败保留输入并显示字段或
操作错误。请求完成后刷新服务端数据，成功反馈以真实响应为准。停用/删除只影响后续新购买，
历史订单继续使用购买时快照。

## API 与后端实现

- `GET /api/v1/admin/products`：关键词、会员等级、启用状态及分页，首版返回会员道具记录。
- `GET /api/v1/admin/products/{product_key}`：详情。
- `POST /api/v1/admin/products`：创建。
- `PUT /api/v1/admin/products/{product_key}`：更新商品；URL 指向原键，响应返回更新后的商品与键。
- `DELETE /api/v1/admin/products/{product_key}`：删除。

路径参数由客户端编码；后端对全部接口验证 Admin JWT，并通过独立 `ManageProducts` 权限
授权 owner/admin。保持已有统一响应与 HTTP 错误约定：无效输入 400，未登录 401，
无权限 403，不存在 404，重复键 409。权限以服务端为准。

后端按六边形架构新增商品领域校验、repository port、application service、SQLx adapter、
web DTO/handler/router，避免在 handler 堆业务逻辑。DTO 与前端类型同步。
写操作与审计记录使用同一事务，记录管理员、操作、目标和变更；SQL 使用参数绑定。
输入校验覆盖金额、键格式、支持等级、道具 ID、名称、UUID 和 V3 限制；重复键不能覆盖原记录。
复用现有商品表，不新增或覆盖种子数据，不改微信支付密钥和回调配置。

## 验证与交付

1. 前端表单测试覆盖金额到整数分、UUID/V3 限制、编码业务键、会话失效及 API 错误。
2. Bun 测试与 TypeScript/Vite 构建通过。
3. 若补后端：领域和授权测试、隔离 PostgreSQL CRUD 与审计事务测试通过。
4. 后端代码变更后重启本地后端，才进行 API 联调；不在旧进程验证新行为。
5. 浏览器验证登录、真实列表、筛选、新建/编辑/启停/删除、失败保留输入、退出、
   深浅主题、桌面与窄屏布局。真实生产商品不用于删除测试。
6. 更新根 README、FEATURES、CHANGELOG 和项目文档，明确实际实现状态和启动命令。

此次交付为代码和本地验证；生产部署及 Nginx 变更需要另外明确安排。
最终报告明确区分本地后端重启状态与生产未部署/未重启状态。
