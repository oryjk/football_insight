# 用户来源追踪设计

日期：2026-10-18
状态：实现与本地验证完成，待负责人执行迁移及发布（设计由 Claude 与产品负责人讨论后撰写）

## 背景与目的

产品负责人在抖音有账号，发布内容后会带来注册。2026-04-23 一条产品截图视频的前后，
`f_i_users` 的注册量明显抬升（4/23 当天 88 人、4/24 为 65 人），但用户表没有任何来源字段，
只能靠时间吻合推断，无法证明这些注册来自抖音，也无法比较各渠道的质量。

目标：**能回答「每个渠道带来了多少注册、多少留存、多少付费」**，以便决定内容和渠道投入。

## 目标

1. 记录每个新用户的首次来源（渠道 + 具体内容/活动）。
2. 支持按渠道、按内容统计：注册数、次日/7 日回访、是否发生付费。
3. 零成本接入运营：新增一个渠道或一条视频，只需要生成一个带参数的入口，不需要发版。

## 非目标

- 不做完整的归因模型（多触点、时间衰减）。只记首次来源。
- 不收集设备指纹、手机号、IP 等额外个人信息。
- 不改变现有登录、邀请码、会员、支付逻辑。
- 不把来源展示给普通用户。

## 反目标（出现即算失败）

- 来源记录失败导致注册或登录失败。来源只能是尽力而为的附加信息。
- 老用户回访时覆盖首次来源。
- 通过来源参数可以注入脚本、超长内容或伪造他人身份。

## 现状（实现前请自行核对）

- 小程序登录：`uni.login` → 后端 `login_with_mini_wechat`；未绑定账号时返回
  `BindingRequired`，走 `bind_wechat_mini_program_account` 完成注册/绑定。
  相关代码：`football_insight_service_backend_rs/src/auth/`，小程序侧
  `football_insight_mini/src/api/auth.ts`、`src/stores/appSession.ts`、`src/pages/user/loginFlow.ts`。
- 公众号：`handle_wechat_webhook` 处理 `subscribe` 事件并生成邀请码。
- 邀请码推荐关系和会员等级（V1–V9）已存在，**来源追踪是另一件事**，不要复用邀请关系字段。
- `f_i_paywall_events` 已有付费墙埋点；`f_i_users` 无来源字段。

## 方案

### 1. 来源参数约定

统一使用两个参数，由小程序码、分享链接、公众号菜单携带：

| 参数 | 含义 | 示例 |
|---|---|---|
| `src` | 渠道 | `douyin`、`wechat_oa`、`xhs`、`share` |
| `cid` | 具体内容或活动，由运营自定 | `20261018_reflux_board` |

规则：只允许 `[a-z0-9_-]`，`src` 最长 32，`cid` 最长 64；不合法的值丢弃（记为空），不报错。
小程序码用 `scene` 传参时需要压缩成单个字符串（`scene` 限 32 字符），格式建议
`s=douyin&c=0418a`，由实现方定义短码表或编码方式，并在文档中说明。

### 2. 小程序端采集

- 启动时读取 `uni.getLaunchOptionsSync()` 的 `query`、`scene`，解析出 `src` / `cid`。
- 把解析结果存到本地（建议 storage），**只在尚未存在时写入**（首次来源优先）。
- 登录/注册请求时把它作为可选字段带给后端。老版本客户端不带此字段，后端必须兼容。
- 解析、存储逻辑放 `src/utils`，不要放进页面；遵守 `scripts/check-import-boundaries.mjs`。

### 3. 后端存储

新增迁移（时间戳必须大于现有最新迁移，目前为 `20261017140000`；迁移不随部署自动执行）：

- 新表 `f_i_user_acquisitions`：`user_id`（主键，引用 `f_i_users`）、`src`、`cid`、
  `landing_scene`（可选，原始 scene 数值）、`created_at`。
- `user_id` 主键即保证每人只有一条，写入使用 `INSERT ... ON CONFLICT DO NOTHING`。
- 不修改 `f_i_users`，降低迁移风险。

在用户首次创建成功的同一用例里写入来源；写入失败只记日志，不影响注册结果。
遵循项目现有分层：业务逻辑在 `application`，SQL 在 `adapters`，不要写在 web handler 里。

### 4. 统计查询

提供只读统计，二选一（实现方决定）：

- 管理后台 `/api/v1/admin/**` 新增一个接口，返回按 `src`、`cid` 分组的：注册数、
  次日回访数、7 日回访数、付费用户数。
- 或先提供一份可直接运行的 SQL（放 `docs/sql/`），后台接口后做。

回访口径使用现有登录记录（`record_user_login`）；付费口径使用已支付订单。
**统计口径中不要混入抢票余票类数据**（那类数据有「开票后 10 分钟」的特殊口径，与本功能无关）。

### 5. 公众号入口

公众号 `subscribe` 事件携带场景值时，可以记录关注来源。此项为可选的第二阶段，
首期不做，避免与邀请码逻辑耦合。

## 隐私与合规

- 只记录运营自己定义的渠道标识，不记录第三方平台的用户标识。
- 若隐私政策未涵盖「来源统计」，请提示产品负责人补充，不要自行修改隐私文案。

## 验收标准

1. 带 `src=douyin&cid=test1` 的入口首次注册，生成一条来源记录。
2. 同一用户再次登录或从别的来源进入，来源记录不变。
3. 不带参数、参数非法、老客户端请求：注册正常，不产生来源记录或记录为空，不报错。
4. 来源写入失败（可模拟）时，注册仍成功。
5. 统计结果能按 `src`、`cid` 给出注册数。
6. 通过测试：后端 `cargo test`；小程序 `bun run type-check`、`bun test`、
   `bun run check:boundaries`。

## 首期实现约定（2026-10-18）

- 可选字段为`acquisition: {src, cid?, landing_scene?}`；合法src才形成来源，cid非法独立丢弃。渠道不使用固定白名单，新增运营标识不发版。
- scene采用`s=douyin&c=0418a`，解码后总长最多32 ASCII字符，c直接作为内容短码，运营维护释义；不新增服务端短码表。数值landing_scene单独保存，不存scene原始文本。
- 首次合法来源冷/热启动均可采集，直接参数优先，后续/退出不覆盖；会话调用层装配可选字段，API层仅序列化，遵守现有工具白名单。
- 统计选择只读SQL。现有record_user_login只更新最后登录快照，因此回访明确为D1+/D7+累计代理：最后登录至少晚于注册24/168小时，并提供成熟样本分母；不宣称严格自然日留存。未增加登录历史机制。
- 仓库显式区分INSERT新建与旧账号reactivation，后者及既有账号绑定/登录不记录新获客。独立异步任务、超时与专用连接池隔离来源故障。
- 迁移与真实SQL在无网络的一次性本地PostgreSQL16容器内用全新模拟数据验证，并ROLLBACK确认表不存在；未连接生产做写入/DDL，未执行生产迁移、部署或上传。
- 接入/口径/隐私提示见[用户来源追踪](../../acquisition-source-tracking.md)，完整验收与验证见[验证报告](../../acquisition-source-tracking-validation.md)。
