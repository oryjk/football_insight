# 商品购买记录与会员商品补齐实施计划

> **For agentic workers:** 使用现有前后端分工实施，完成后独立审查；各业务测试先失败再通过。

**Goal:** 补齐 V7/V8/V9 商品，并按商品查询去重购买人数和真实订单的昵称、头像、购买/到期时间、金额。

**Architecture:** Admin 只读购买查询保留 domain/application/ports/PostgreSQL/Web 边界。商品新增不可变 UUID，订单保存商品关联快照，避免可编辑业务键、价格或微信道具 ID 改变后丢失历史。前端使用现有 React/Bun/Tailwind 控件与 Token。

## 约定

- V7/V8/V9 使用 59/79/99 元、12 个月、公开范围，名称参照 V6。微信 ID 的拟用模板为 `fi_v7_year_59`、`fi_v8_year_79`、`fi_v9_year_99`，用户已确认这些道具均已在微信发布，可直接启用。
- `GET /api/v1/admin/products/{product_key}/purchases?page=1&page_size=20` 验证 Admin JWT 与 `ManageProducts`；禁止缓存。
- 返回 `summary`（`purchased_user_count`、`purchased_order_count`、`refunded_order_count`、`total_amount_cents`），分页 `items`、`total`、`page`、`page_size`。
- 订单字段：`order_no`、`user_id`、`user_nickname`、`user_avatar_url`、`paid_at`、`expires_at`、`expiry_source`、`amount_cents`、`status`。
- 购买记录只包含成功付款（`paid_at` 非空且状态 paid/refunded）；购买人数按账号去重，退款保留展示并标明。金额取订单原实付，不随商品现价变化。
- 到期时间优先订单权益快照；没有虚拟支付元数据的历史普通支付按原一年规则计算并标记 `legacy_year`。无法可靠恢复的时间显示未记录，不使用用户当前会员到期时间。
- 历史订单只按唯一、明确的等级/实付金额映射；存在虚拟支付元数据时还要校验道具 ID。没有明确等级的旧 `membership` 订单不猜测归属。
- SQL 迁移只增加字段/索引并谨慎回填；新订单原子保存商品关联。删除后同业务键重建的商品不得吸收旧商品订单。

## 任务与验证

1. **后端与迁移**：补齐稳定商品标识、订单关联、购买查询及 DTO。隔离 PostgreSQL 测试覆盖重复购买去重、退款/未付款区分、分页一致性、实际金额/期限、历史关联和商品改价改 ID 后记录保留、删除重建隔离、鉴权和参数错误。
2. **前端**：每行增加购买记录入口，展示总人数与订单分页；昵称/头像、时间、金额及状态明确。测试编码路径与专属部署前缀、取消请求、摘要独立于当前页、金额/日期/缺失头像、历史到期说明；浏览器验证分页、空记录、错误重试和窄屏。
3. **商品补齐**：生产事务仅新增缺失 V7/V8/V9，复制 V6 期限与公开范围、按公开标价设置金额并记录审计；不覆盖已有商品，不擅自启用未经确认的微信 ID。
4. **上线**：提交与推送本次功能，生产先应用经测试的 additive 迁移再发布后端，重启 local233 与 peiqian；发布 `/football-admin/` 静态页面。只读验证实际商品和订单，所有测试写入均在隔离库。

## 审查重点

- 订单关联不能仅用当前微信 ID 或可变业务键；没有明确归属的历史订单不能被错误计入。
- 当前用户会员状态、退款后的状态或商品期限修改不能改写订单购买时的期限。
- 摘要跨所有页聚合，分页总数与记录处于同一数据库快照，金额按分计算。
- 快速切换商品/页、关闭窗口、退出和鉴权失效不能显示上一请求的迟到结果。
- 迁移与现有版本兼容；未确认的微信道具不能成为可下单的启用映射。
