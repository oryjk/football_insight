# 虚拟支付接入

用户已确认：会员、比赛 ID 解锁和回流提醒一起接入官方虚拟支付；后台审核、签约完成后再配置密钥和商品。本次直接在当前会话实施，保留工作区原有文档改动。

## 设计与约束

- 保留现有下单路由、价格与权益；新增付款前会话准备接口，以新的微信登录 code 交换 session_key，并验证微信身份与登录账号的绑定一致。密钥仅在服务端，生产默认关闭虚拟支付。
- 所有新数字服务订单只生成虚拟支付参数。未配置、旧客户端、H5 或不支持的微信版本不得回退普通支付。历史普通订单仍允许原回调结算。
- 商品映射按业务商品和实际支付金额配置；会员补差价采用独立的固定价格商品，避免后台商品价格与收银台金额不一致。
- 新增虚拟订单元数据、支付渠道、微信订单号、退款记录及权益快照。应用层依赖 ports；签名、微信 API、回调加解密、SQL 分别在 outbound adapters。
- 发货前核对订单、openid、商品、环境、数量、金额；事务内结算一次。退款仅影响来源于该订单的权益，保留后续购买和管理员修改。
- 查单补发只访问当前账号的订单；服务端定时补偿 pending 订单，前端付款成功后等待权益确认，不能凭客户端 success 发放权益。
- 审核中会员购买页显示明确状态，不再为空白页面。配置未完成时显示暂不可购买。
- 不自动部署生产、不提交密钥、不发起真实收费。后端本地验证前先重启，验证使用隔离数据库。

## 实施步骤

1. domain/ports：商品映射、虚拟支付参数、事件与 typed errors。验证签名固定向量、价格不匹配、非法商品和账号错配。
2. adapters：微信 session/access token、签名和查单 API、回调验证与解析、订单元数据及事务结算/退款。测试伪造/重复/乱序回调，查询结果与订单不匹配。
3. application/bootstrap：复用三种下单流程，切换支付 provider，新增准备/状态/回调接口及补偿任务；普通回调不能结算虚拟订单。
4. mini：统一付款工具、会话准备、能力判断、账号切换防护、支付后确认；三条购买链路同时迁移，H5 降级。测试拒绝旧参数、取消/失败、在途账号切换和支付确认延迟。
5. 验证：cargo fmt/check/test/clippy 和架构扫描；bun test/type-check/边界扫描/H5/离线小程序构建；隔离 PostgreSQL 测试重复通知、回滚与退款；本地后端重启后验证未配置状态。
6. 记录：更新项目能力与变更记录，补充后台商品和密钥配置、回调 URL、上线验证及申诉材料准备步骤；对完整 diff 做独立审查。
