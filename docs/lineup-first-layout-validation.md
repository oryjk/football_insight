## 现象与代码证据

用户截图中已选 4-3-3、已排 11/11，但头像重叠于左上角。阵型配置、初始首发及展示模型本身给出 11 个分散坐标；已有代码也为 movable-area 设置了 100% 宽高。

LineupPitch 原来只测量 `#lineup-pitch-field`，得到外层尺寸后，在同一批更新中创建 movable-area 和全部 movable-view，未查询原生区域实际布局。这留下了原生区域尚未布局、位置先被限制在原点的时序风险，与截图症状一致；尚未在用户的微信运行时读取实际原生区域尺寸。

对真实 SFC 添加挂载回归，在旧实现上观察到：回复外层尺寸后已经出现 11 个 movable-view，且没有对原生区域的尺寸查询。两个初始回归先因这两个断言失败，修复后通过；后续增加默认区域尺寸、窗口变化、过期回调和只读状态覆盖。

## 修改

- 外层测量成功后先单独创建 movable-area，并明确绑定测得的 px 宽高，保留原来的百分比 CSS 兜底。
- 下一 tick 查询 `.pitch__area`，只有实际尺寸与目标一致（容许亚像素差异）才显示球员；未布局或仍为默认小区域时有限重试。
- 窗口尺寸变化后重新确认原生布局，位置仍由原有比例坐标与 boxPositionPx 计算，不改阵型、球员或用户自定义坐标。
- 测量带请求代次，旧回调不能放行新布局；组件卸载后取消重试，忽略迟到回调。
- 保存、发布、草稿恢复、拖动互换及点击判定逻辑不变。
